## Chapter 8: Serving Agentic Workloads on the NVIDIA Stack — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | NIM vs Triton vs TensorRT-LLM — what does each do in the serving stack? | NIM: packaged, containerized microservice for a specific model with a standard API (often built on Triton + TensorRT-LLM). Triton: general multi-framework/multi-model serving server (TensorRT, PyTorch, ONNX, Python, vLLM backends), supports ensembles. TensorRT-LLM: compiler/runtime that builds optimized, quantized LLM inference engines. Exam tip: NIM = fastest to deploy; Triton = most flexible multi-model; TensorRT-LLM = deepest LLM-specific optimization. |
| 2 | Which NVIDIA GPU generation introduced native FP8 Transformer Engine support? | Hopper (H100/H200), continued in Blackwell. Exam tip: FP8 quantization is the recommended balance of speed and accuracy on Hopper-class and newer GPUs. |
| 3 | What is continuous (in-flight) batching? | A batching strategy where new requests can join and completed requests can leave the active batch at each decoding step, instead of waiting for a fixed batch to fully complete. Exam tip: this maximizes GPU utilization for variable-length LLM outputs and is a core TensorRT-LLM feature. |
| 4 | What problem does paged KV-cache management solve? | Memory fragmentation from allocating contiguous KV-cache buffers per sequence. Paging allocates cache in fixed-size blocks, allowing more concurrent long-context sessions in the same GPU memory. Exam tip: critical for serving SLAs with long context windows and many concurrent users. |
| 5 | INT8 vs FP8 vs INT4 (AWQ/GPTQ) — trade-off summary | INT8: moderate speedup, moderate accuracy risk without careful calibration. FP8: near-FP16 accuracy on Hopper/Blackwell with ~2x compute throughput vs FP16. INT4 (AWQ/GPTQ): highest speed/memory savings, highest accuracy risk. Exam tip: pick FP8 when accuracy matters most; INT4 when memory/speed dominate and some accuracy loss is acceptable. |
| 6 | Basic command to run an NVIDIA NIM container | docker run --gpus all -p 8000:8000 nvcr.io/nim/<org>/<model>:<tag>. Exam tip: NIM containers expose an OpenAI-compatible REST/gRPC API by default — no custom API code needed. |
| 7 | How does Triton organize models for serving? | Via a model repository directory: each model has its own folder containing versioned subfolders and a config.pbtxt defining inputs/outputs, backend, and batching settings. Server launched with: tritonserver --model-repository=/models. Exam tip: config.pbtxt is where dynamic batching and instance groups are configured. |
| 8 | What factors does KV-cache memory size scale with? | Roughly: 2 (K and V) × num_layers × num_heads × head_dim × sequence_length × batch_size × bytes_per_element. Exam tip: longer context and larger batch size directly multiply KV-cache memory — a key lever exam scenarios test when memory runs out. |
| 9 | Dynamic batching vs continuous batching — which is better for LLM token generation? | Continuous (in-flight) batching, because it doesn't force all sequences in a batch to finish together — it swaps requests in/out per generation step. Dynamic batching (grouping requests within a time window) is more suited to fixed-shape, single-forward-pass models (e.g., vision models). Exam tip: TensorRT-LLM's in-flight batching is the LLM-specific evolution of Triton's dynamic batching. |
| 10 | When should you use NIM vs building a custom TensorRT-LLM engine? | Use NIM for supported models needing fast, standardized deployment with minimal tuning. Build a custom TensorRT-LLM engine when you need model-specific optimization control (custom quantization, kernel tuning, or an unsupported architecture) beyond what a packaged NIM offers. Exam tip: exam scenarios testing 'fastest time-to-production' point to NIM; scenarios testing 'maximum custom optimization control' point to raw TensorRT-LLM. |
| 11 | Approximate FP8 vs FP16 compute throughput advantage on H100 Tensor Cores | FP8 Tensor Core throughput is roughly 2x FP16 Tensor Core throughput on H100 (per NVIDIA Hopper architecture specs). Exam tip: this is why FP8 is favored for latency/throughput-sensitive LLM serving when accuracy tolerance allows it. |
| 12 | How do you match a serving configuration to a stated latency vs throughput SLA? | For low-latency SLAs: smaller batch sizes/windows, higher-precision or FP8 (not aggressive INT4), fewer concurrent sequences per GPU. For high-throughput SLAs: larger batches, continuous batching enabled, more aggressive quantization (INT8/INT4) to fit more concurrent requests. Exam tip: exam scenarios explicitly state latency (ms) or throughput (req/s or tokens/s) targets — match batching/quantization choices accordingly, don't default to 'more batching is always better'. |
